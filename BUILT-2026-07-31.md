### B29 — the two halves that could be built

**The English lexicon had no frequency data.** The order suggests proving the gain
with `cargo run --example spellrate`. That harness measures the **miss rate** — how
many words of a text are not in the lexicon — and frequency data does not change it
by one word. So the gain is measured on what actually changed, and both numbers are
in `tests/spell_en.rs`:

```
substitution typos (tje, fpr, wjth, thst, hsve, ppint, …):  4/10 first → 9/10
transposed typos  (teh, adn, thier, liek, jsut, …):        11/12 → 12/12
```

The second number is the honest one to lead with: the transposition rule was already
doing that work, and frequency bought **one** of those twelve. It is in the report
because rolling both into a single flattering figure would be the thing this project
keeps taking out of its own documentation.

**And it found a bug in the ranking beside it.** The proper-noun penalty was half an
edit, and half was not enough to do the job the half was for:

```
before:  tge → GTE, age, mtge, tee, the, tie, toe      (the telephone company, first)
         amd → AMD, mad, ADM, Adm, and, ad, add, aid   (`and` fifth)
after:   tge → the, GTE, age, …
         amd → mad, and, AMD, …
```

`GTE` is a *transposition* of `tge` and a transposition is worth two edits of
advantage, so half an edit of penalty could never overcome it. It costs a whole edit
now.

**One case deliberately not fixed**, and written into the test rather than quietly
worked around: `amd` still offers `mad` first, because `mad` is a transposition and
`and` is only a substitution. Making frequency win there means widening the bands
past a transposition's advantage — which is the invariant that stops `the` being
offered as the correction for `then`. One misordered suggestion is the cheaper
mistake and `and` is second.

**Hebrew got nothing**, on purpose. A frequency order for Hebrew that covered
seforim rather than newspapers is real work, and guessing at one would be invented
evidence in the language this project is actually for.

**The dictionary is a file now** on the desktop, merging in whatever the browser
had. With a caveat that has to be stated plainly: B29 asks for *"a file the desktop
app and the browser both read"* and **a browser cannot read a path.** That is a
sandbox fact, not a missing feature. The desktop half is built; the claim is not.

## 12. The mefarshim bug — how I introduced it and how it was caught

This is the most important thing in this report, because it is a defect I created
while fixing defects, in the exact class I had spent the week removing.

**W43** added the Otzaria-style reading model: tick commentators, mark the lines
they speak about, click a line to read them. `Marks::of` built that index from
`inbound.jsonl`, and it treated **every incoming `comments-on` edge** as a mefaresh
on the sefer.

That is inferring a relationship between two seforim from the existence of an edge.
It is BUILDER.md rule 6. I had written the orientation layer that fixed the same
class of error four days earlier.

**The number that should have been the tell:**

```
bavli/berakhot                30 works with commentary edges landing in it,  30 real
shulchan-arukh/orach-chayim   48                                          ,  17 declared
tur                           40                                          ,   4 declared
```

My one corpus test read Berakhot, where the graph is clean. **One masechta is not
the corpus.** The user found it by opening the Tur.

**Why the obvious fix was wrong too.** *Keep only the declared commentaries* would
have dropped the **Kaf HaChayim** — the largest mefaresh on Orach Chayim, 29,956
edges, and Sefaria declares nothing for it — along with the **Beit Yosef**, 18,353
edges of *the* commentary on the Tur.

What separates them is Sefaria's own filing, and `is_commentary_on` asks two
questions, both of them the corpus's own statements: does it **declare** this base,
or does it stand on a **commentary shelf** whose shelf-above is the shelf this sefer
stands on. No slug parsing.

```
tur                          40 → 5 mefarshim   (and the Beit Yosef is GAINED)
shulchan-arukh/orach-chayim  48 → 21
genesis                      73 → 58
bavli/berakhot               30 → 30
```

The test that now exists and did not:
`nothing_is_offered_as_a_mefaresh_that_is_not_one_anywhere_on_the_shelf`, over seven
seforim from five different parts of the shelf. And
`the_seforim_the_reader_named_are_gone_and_the_real_ones_are_not`, which names all
three of the reader's examples on the real graph rather than asserting a count that
would go green again for some unrelated reason.

`Marks::refused()` keeps the count of what was turned away — thirty-six on the Tur —
because a filter nobody can count is a filter nobody can check.

**The Pri Megadim was not mine.** Sefaria's data disagrees with itself in one line:

```
peri-megadim-on-orach-chayim  ['Halakhah','Shulchan Arukh']
peri-megadim-on-yoreh-deah    ['Halakhah','Shulchan Arukh','Commentary','Pri Megadim']
```

Same author, same sefer, two chalakim, two filings — so one stood beside the four
chalakim as though it were a fifth. It declares `commentary_on:
shulchan-arukh/orach-chayim`, so a declaration now outranks a category in
`shelf_of`. Exactly one work on that shelf moves, verified against the real index.

## 15. W31 and W35 — the two filed from OtzariaSonim

Both came from the keypad-phone reader migrating onto this corpus, and they are the
only two orders in this round filed by a *consumer* rather than by the grade.

### W31 — the summary file could not summarise

A `touching.jsonl` row was `{"a": …, "t": "comments-on"}`. Nobody asks *does this
segment have a `comments-on`*; they ask **does it have one from the mefarshim I have
selected**, and the field that answers that was the one not stored. So the only way
to answer was `inbound.jsonl` — 27.3 MB and 156,076 edges against this file's
1.15 MB, which on a phone with a 192 MB heap is the difference between opening
שולחן ערוך and an `OutOfMemoryError`.

Rebuilt over all **4,182,337 edges** in 637 s. Orach Chayim now:

```
rows naming a source work:  68,386 of 69,443  (98.5%)
distinct seforim filterable:   652
top five:  kaf-hachayim 5,504 · mishnah-berurah 5,011 · magen-avraham 4,504
           beer-hagolah 4,166 · eliyah-rabbah 3,863
```

The 1.5% that name nothing are self-edges, where source and target are the same
sefer — left off deliberately, because *this sefer is its own source* is true and
useless to a filter.

**The obvious encoding was wrong, and only measuring showed it.** One row per work:

```
summary layer:  261 MB  →  636 MB      the summary is 92.4% of what it summarises
inbound.jsonl:  0.69 GB
```

A summary the size of what it summarises is not a summary — the first version would
have quietly repealed the order's own justification **while passing every test.** So
the works are grouped onto the `(anchor, type)` row, and the anchor is written once
for the two hundred seforim that comment on a se'if:

```
summary layer:  261 MB  →  471 MB      68% of inbound, largest file 4.56 MB
Orach Chayim:  1.15 MB  →  4.14 MB     23,426 rows, 652 seforim filterable
```

Still bigger than it was, and that is the price of answering the question at all —
165 MB cheaper than the shape that had not thought about it.

**A false alarm worth recording, because it was my instrument and not the code.**
Midway through this I ran the suite and got a failure —
`what_i_wrote_and_who_quotes_it_come_back_from_one_call`, *"the Rambam on this
mishnah is one of them"*. The cause was that `girsa-link-types` rewrites
`inbound.jsonl` as well as `touching.jsonl`, and it was **still running**: the test
was reading a half-rebuilt cache. Re-run against a settled corpus: **756 passed, 0
failed across 69 suites.**

Worse than the false alarm was how nearly I missed it. I had been summing test counts
with `grep -E "^test result: ok"`, which filters the `FAILED` line out — so a broken
tree reported a clean total, and I committed on it. The count now comes from
`^test result` with the failure column summed too.

Read is a **merge and not first-wins**, which is its own small correctness argument:
a run is many flushes, so one se'if's works can be split across two rows of the same
file, and keeping the first row would be the filter answering *wrongly* rather than
slowly. Wrong is the worse of the two.

### W35 — answered, with a measurement that changed the answer's shape

W35 asks whether `segments.jsonl` should become `text.txt` plus a sidecar so that
spec.md §4.1's *greppable, diffable* stops being aspirational. It is a careful
order: it states plainly that its own line-addressed format is unacceptable here and
asks only for the half that is not in tension with permanent ids.

**The answer is no, not yet — because the split does not buy the thing it is for.**

```
Shulchan Arukh, Orach Chayim
  segments:                            4,171
  containing inline markup ('<'):      4,170   (100.0%)
  containing a newline:                    0
  grep -c "יתגבר כארי" segments.jsonl:     0
```

That phrase is in the sefer and `grep` cannot find it. **Moving the text into a
`.txt` would not change that by one hit**, because what defeats the grep is `<b>` and
`<span>` sitting between the words in *every single segment*, not the JSON envelope.
One and a half of four claims delivered, for two files per work and an asymmetric
half-failure mode.

It becomes right **after W34**, which already has to take the anchors out of the
text — so **W34a** is filed: strip the presentational markup in the same pass and
assert *the text of a segment contains no `<`*. Worth doing on its own account,
independently of any file format, because a search index built over text with tags in
it is an index whose tokens include `b` and `span`. That is true today, in 100% of
that sefer.

Two things W35 got right, recorded for whoever does this later: **no segment contains
a newline** — 0 of 4,171 — so the "a text file cannot hold one" worry is a
contingency and not a design constraint; and the line-count invariant is the right
guard and has to be written the day the format changes, not after.
